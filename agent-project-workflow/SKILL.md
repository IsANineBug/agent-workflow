# Agent Project Workflow

## 0. 这个 skill 做什么

让 agent 在**任何全新项目动手写代码之前**，先走完「采访 → SPEC → PLAN → 上下文工程文档体系」。

它交付的不是代码，是**一份给未来 agent 的说明书**。所以它要解决的核心问题不是「文档写得漂不漂亮」，而是 **「agent 读了但没照做」**。

### 该触发

| 用户说 | 英文对应 |
|---|---|
| 「我想做个 X」（X 是**项目级产物**） | "start a new project" |
| 「帮我开个新项目 / 搭个架子」 | "kick off a new project" / "bootstrap a new repo" |
| 「从零开始做一个 X」 | "build X from scratch" |

### 不该触发

| 用户说 | 为什么 |
|---|---|
| 「给现有项目加个大模块」 | 本 skill 只服务全新项目，会覆盖已有文档 |
| 「重构一下这个项目」 | 改现有代码，流程不同 |
| 「修个 bug / 改个函数」 | 单点修改不需要整套流程 |
| 「我想做个函数 / 做个按钮 / 写段脚本」 | 含「我想做个」但**不是项目级产物** |

## 1. 前置检查（进入流程前必做）

**顺序不能颠倒。**

**第一步 · 确认目标目录。** 不要假定当前工作目录就是目标目录。
用户在 `~/work/`（里面一堆项目）说「我想做个记账 App」，本意可能是在 `~/work/bookkeeping/` 新建 —— 此时直接拒绝就是**拒错了**。先问「你要在哪个目录建？」。

**第二步 · 判定是否全新。** 目录为空，或只含 `.git/`、`README.md`、`LICENSE`、`.gitignore` 等无害文件 → 视为全新。

**第三步 · 已有文件就停。** 若目标目录里有源码、构建配置，或已有的 `SPEC.md` / `PLAN.md` / `AGENTS.md` → **停止流程**，说明本 skill 只服务全新项目，并给出两个选项：换一个空目录 / 放弃本流程。

任何创建动作都发生在第三步通过之后。

---

## 2. 采访流程

**每轮 3–5 问，最多 5 轮。** 3–5 是**上限，不是配额** —— 信息够了就问 3 个收工，硬凑 5 个只浪费用户时间。

- **用选项式提问**：给 2–4 个选项 + 一个推荐，并允许用户自由填写。
  一个开放问题用户要打 200 字，一个选项式问题他点 3 下就传完了。
- **每轮结束必须复述**：「我理解你要的是……，对吗？」一次复述挡掉的问题，比多问 5 个还多。
- **第 3 轮后先出「功能清单草稿」**给用户勾选/划掉，再继续。
  **草稿只在对话里展示，不落盘** —— 落盘会与最终 SPEC 形成两个来源。
- **到第 5 轮必须停止提问**，即使仍有空白，也改为在 SPEC 里标注「待定」并说明。

### 建议的提问方向

| 轮次 | 问什么 |
|---|---|
| 1 | 目标、给谁用、解决什么问题 |
| 2 | 功能清单（给候选让用户勾） |
| 3 | 明确不做的事（最容易被漏，也最值钱）→ 出功能清单草稿 |
| 4 | 验收标准：用户做什么 → 能看到什么 |
| 5 | 技术约束、风险、边界 |

每轮结束**更新 `docs/KICKOFF-STATUS.md`** 的采访进度。

---

## 3. 确认词与确认记录

**确认必须指向对象。** 句子里要同时出现**确认动作**和**对象**。

| 算确认 | 不算确认 |
|---|---|
| 「SPEC 确认」「PLAN 通过」 | 「OK」（单独出现） |
| 「我确认 SPEC.md」「SPEC 批准」 | 「没问题」「看过」「我看看」「还行」 |
| 「approve the SPEC」「SPEC confirmed」 | 「先这样」「可以」（无对象）/ 沉默 / 用户没反驳 |

- 动作词：确认 / 通过 / 批准 / approve / confirmed / LGTM
- 对象词：SPEC / PLAN / SPEC.md / 计划

**缺一就追问**：「这是确认吗？确认后我才开始写 PLAN。」

确认后把**原话与时间**写入 SPEC.md 的确认记录表。
SPEC 内容在确认后被修改 → 原确认失效，需要重新确认。

---

## 4. 两道门禁

| 门禁 | 触发条件 | 允许 | 禁止 |
|---|---|---|---|
| 一 | SPEC 未确认 | 建目录、`git init`、写白名单内文件 | 生成 PLAN.md、写白名单外文件、装依赖 |
| 二 | PLAN 未确认 | 写文档、调整 PLAN | 写白名单外文件、装依赖 |
| 放行 | SPEC + PLAN 均确认 | 按 PLAN 逐步实现 | 跳过步骤、擅自加功能 |

### 4.1 文件白名单

门禁一、二期间**只允许**创建：**目录**、**`*.md`**、**`.gitignore`**、**`LICENSE`**。

其余一律禁止：`.json`、`.yaml`、`.toml`、`.txt`、`.sh`、`Makefile`、`Dockerfile`、任何语言的源文件。

为什么用白名单而不是「禁止源码」：「源码」这个词太模糊 —— `package.json`、`Makefile` 是配置不是源码，但会实质影响项目。模糊的规则会被按自己的理解执行。

### 4.2 依赖边界

禁止的不只是包管理器（`pip install` / `npm install` / `cargo add`），还包括任何**改动系统或全局环境**的命令：`nvm use`、`rustup`、`apt install`、修改全局配置。

`git init` 是唯一例外 —— 它属于「建目录」的一部分。但本 skill **不管 git 提交**，提交节奏由用户自己处理。

### 4.3 放行时必须明说

门禁**无法技术强制**，它依赖 agent 遵守指令。所以每次放行都要说出一句：

> 「SPEC 与 PLAN 均已确认，现在开始第 1 步：X」

静默放行与明说放行的差别很大 —— 后者用户能当场发现违规。

---

## 5. SPEC 完整度门禁

SPEC 生成后、进入确认环节**之前**，自检这四项：

| 检查项 | 要求 |
|---|---|
| 功能清单 | ≥ 1 条 |
| 每条功能的验收标准 | 必填，不得为空 |
| 明确不做的事 | ≥ 1 条（确实没有时，也要显式写「暂无」，并请用户确认这一句） |
| 适用边界 | ≥ 1 条 |

**不通过 → 不允许请用户确认**，先补齐，或说明为什么补不齐。

理由：没有「不做的事」的 SPEC，等于一份谁都能往里塞需求的空框架 —— 门禁就白设了。

---

## 6. 执行中变更

SPEC 与 PLAN 都确认、**已开始实现之后**，用户改需求 → **一律回到门禁一**：

1. 改 SPEC.md（记一行变更日志）
2. 请用户**重新确认 SPEC**
3. 重新确认后，改 PLAN.md
4. 请用户**重新确认 PLAN**
5. 继续实现

已完成的步骤**不重做**，但要检查是否被新需求影响；受影响的步骤在 PLAN 里标注。

为什么这么严：门禁如果只在「开始前」有效，开工就失效了 —— 而开工后改需求恰恰是最常见的情况。

> 这条规则代价高，容易被绕过。如果你（agent）认为本次变更很小、用户也同意跳过，**必须在 SPEC 的变更记录里留一行豁免**，写明原话与时间。不留痕的绕过就是违规。

## 7. 退出规则

**任何阶段**，用户说「停止 / 算了 / 不做了 / 放弃」→ 立即停止：

- 不再生成或修改任何文件
- **不删除**已生成的文档（删除是破坏性操作，交给用户）
- 在 `docs/KICKOFF-STATUS.md` 记一行「已放弃」与时间
- 用一句话说明当前停在哪儿、已产出了什么

## 8. 产出物与生成顺序

```
项目/
├── docs/
│   ├── KICKOFF-STATUS.md   ← 采访开始时创建（最早）
│   ├── GIT.md  DEPS.md  SECURITY.md  BUILD.md  QUALITY.md
├── SPEC.md                 ← 确认记录在此
├── PLAN.md
├── AGENTS.md               ← ≤ 350 行
└── INDEX.md                ← ≤ 300 行
```

**顺序**：`KICKOFF-STATUS → SPEC → PLAN → AGENTS → INDEX → docs/ 其余五个`

为什么是这个顺序：需求 → 计划 → 规矩。AGENTS.md 的约束要能引用 SPEC 的具体条目，倒过来写会产生悬空引用。

### 8.1 模板用法

`assets/` 下有 9 个模板。**用它们，不要从零写** —— 否则每次产出结构都不一样，用户下次找东西要重新探一遍。

| 模板 | 产出 |
|---|---|
| `SPEC.md.tmpl` | 项目 SPEC（门禁与白名单已内联） |
| `PLAN.md.tmpl` | 项目 PLAN |
| `AGENTS.md.tmpl` | 常驻规则 |
| `INDEX.md.tmpl` | 入口索引 |
| `KICKOFF-STATUS.md.tmpl` | 流程状态 |
| `docs/*.md.tmpl` × 5 | 五份规则文件 |

模板里的 `{{占位符}}` 全部替换；`<!-- 填写指引 -->` 注释在生成正式文件时删除。

五个 docs 文件**固定全部生成**，即使内容为「待填」也不缺文件 —— 结构固定，agent 才知道该往哪写。空壳部分在 PLAN 里安排填写时机。

## 9. 上下文工程纪律自检

生成文档后，逐项执行并**报出实际数字**：

| 检查 | 怎么做 |
|---|---|
| 体积上限 | 用 `wc -l` 实测各文件，报出数字，不是「应该差不多」 |
| 硬编码行号 | 全文搜「见 N 行」—— 一条都不该有，改写成搜索配方 |
| 交叉引用 | 逐条核对指向的文件与章节确实存在 |
| 重复事实 | 同一个会漂移的事实（版本号、路径、数量、依赖名）只允许有一个正文处，其余是指针 |

**为什么较真**：规则自己有 bug 比没有规则更糟，因为人会信任它。文档里写的每条命令都应该真能跑、写的每个上限都应该真满足。

上限被突破时，**主动说明并给出处理方案**，不要静默放过。

## 10. 观察记录与 evals 提议

每次真实运行结束后，向**用户可写位置**追加**一行** JSON：

```json
{"date":"2026-09-20","project":"记账app","rounds":3,"gate_bypassed":false,
 "user_corrections":["第2轮说太啰嗦"],"notes":"用户主动要求第3轮出草稿"}
```

写入路径，**按顺序试**：

1. `<skill 目录>/observations.jsonl` —— 记录跟着 skill 走
2. `~/.agent-project-workflow/observations.jsonl` —— skill 目录只读时退回用户主目录
3. 都不可写 → **静默跳过**，只在结尾用一句话说明「本次未能记录观察」。不报错、不中断、不反复重试

**每次追加时顺便统计总行数。** 否则每次都是新会话，agent 永远不知道累计到几次 —— 阈值机制就是死的。

累计到阈值（**3 次运行**，或 **2 次「门禁被绕过」**）→ **主动提议一次**建 evals 用例；用户拒绝后不再重复提。

### 这个记录不评分

skill 自己给自己打分等于学生自己批改考卷 —— 分数好看，问题照旧。它只有一个用途：将来能拿**真实失败**提炼测试用例，而不是凭空想象。

- 一条记录**不等于**一条用例 —— 用例需要「可复现的提示词 + 明确期望行为」，通常得从 2–3 条同类记录里提炼
- 记录**不进项目目录** —— 它的用途是改进 skill 本身，放进项目就是每个项目一份的噪声
- 记录内容**不写进本文件** —— 这里只写记什么字段
- 一次最多写**一行**，30 秒内完成，不打断用户、不要求用户确认

## 11. 能力降级（跨平台）

本 skill 不只服务某一个平台。**指令写能力，不写工具名。**

| 能力 | 有 | 没有时怎么办 |
|---|---|---|
| 带选项的提问工具 | 用工具给选项 | 纯文本编号选项，效果等价 |
| 可写的 skill 目录 | 正常记录观察 | 退回用户主目录；都不可写则静默跳过 |
| `wc` / `grep` 等命令 | 用命令实测 | 用自身能力估算，并说明估算方式 |
| `context-efficient-docs` skill | 调用它做文档体检 | 跳过，只做最小自检（行数估算） |
| 子 agent / 并行执行 | 可用于 evals | evals 改为串行执行 |

各平台的安装路径与**已验证**的降级行为见 `references/platforms.md`。
没验证过的平台不写适配方案 —— 猜出来的适配比留空更危险。

### 已知限制

**硬门禁不是技术强制。** 它是一份指令，agent 愿意遵守才有效；能力较弱的 agent 可能无视它。缓解办法是 §4.3 的「放行时必须明说」—— 让违规可被发现。

**产出文档固定中文。** 英文用户能触发本 skill，但拿到的是中文文档。这是有意识接受的取舍，不是疏漏。
